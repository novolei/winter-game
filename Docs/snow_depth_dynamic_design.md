# 动态雪深：每局独有、可读、可复现的设计提案

## 结论

应该做，但不应把整张山谷当作每帧流体模拟。WinterTime 所需要的是一张会被天气**缓慢改写的冬季地貌**：每局开场已有不同的成熟雪形；降雪、风、遮蔽与踩踏在数十秒到数分钟内留下有意义、可预判的细小改变。玩家应当能读出“背风处更深、风口更薄、旧路更好走”，而不是看见随机噪声在地面爬行。

这个方案保留世界的冷、静与可记忆性：同一局内地貌始终稳定且可学习；换一局才改变它的基础格局；暴雪和风向转变只改写合理的局部。

## 当前事实（不是推测）

- `src/systems/snow_field.gd` 已有 120 m × 120 m、512²、世界锚定的雪深窗口；它的基础雪深由固定 `noise_seed = 20260811`、地形高度与 `scour()` 得出：洼地深、脊线被吹薄。`depth_at()` 目前还会被脚步压实层降低。
- 这意味着基础地形和雪深目前对所有新局固定；窗口滚动时重新从同一噪声函数生成，因此不会随相机漂移。
- `src/systems/snow_accumulation.gd` 的 `cover()` 已随降雪、风和昼夜连续演化，但它目前服务于屋顶、物件、静态车辙的覆雪视觉；**它不改变 `SnowField.depth_at()`**。
- `WindSystem` 已输出连续的强度与方向，`WeatherSystem` 已由 `data/weather/*.tres` 驱动降雪率、风图与阶段；`TrackMask` 已会因风与降雪让动态足迹消退。它们是很好的输入，尚未成为雪深场的输入。
- `Docs/DEFERRED.md` 的旧 W4-1 “没有中间带”结论已在 2026-08-13 被可复现扫描否定：120 m 场的 11,881 个滑动 12 m 方块中有 5,468 个均值落在 0.02–0.32 m；重建旧报告的 80 m / 0.75 m 采样也得到 3,697/8,464 个。旧报告的“41% 超过涉雪门槛”仍可复现（40.55%），但“35% 裸地”和“没有任何中间方块”不能。因此 Phase A 不得为了掩盖一个不存在的缺口而重调 profile；点值分布是否还需要改善，须先由负责人签署目标和首日路线下限。
- 室内地面/门口的 carve 已经是正确的硬约束：建筑内部无积雪、地坪需保持可站立，开门处只能有有限的吹入雪舌。新系统不得覆盖这条规则。

## 物理上可信、游戏上可读的模型

将每个位置的雪深拆成四件彼此可解释的事实：

```text
最终雪深 = 初始成熟雪层 + 新雪沉降 + 风致再分配 - 踩踏/道路压实 - 合法的消融
```

1. **初始成熟雪层（每局一次）**

   开局不是“刚下第一场雪”。它应由运行种子、地形高低、坡向、局部遮蔽、道路/建筑禁雪区和低频相关扰动共同生成。扰动的尺度应是约数米到数十米的雪堆/风蚀区，不是 23 cm 格子噪点。每局可有不同的背风雪袋、可通行脊线与半埋的旧路，但农舍出口、第一日路径、信标落点与剧情构图须仍落在受控安全区。

2. **新雪沉降**

   降雪增加深度，但按暴露度与遮蔽度分配：开阔地接收较多，树冠、屋檐、室内和被风切过的脊线较少。白茫风暴提高输入速率，不应在一个天气切换帧把地面整体抬高；沿用现有 `SnowAccumulation` 的双积分、限斜率原则。

3. **风致搬运，而非“风一来所有雪都少”**

   风应从迎风、凸起、裸露位置拿走少量雪，并将其中有限份额放到下风、凹陷、障碍物背风侧。采用方向性侵蚀/沉积近似即可：按风向查看有限距离的上游/下游邻域，使用预计算的暴露度、坡度和遮蔽度决定输送量。它守恒或近似守恒于活动窗口内，并允许极少一部分被吹出窗口；不做真实流体、雪崩或逐粒子模拟。

4. **压实与缓慢回填**

   脚步继续写入压实层，已踩出的路能稍浅、稍好走；雪落与微弱的 settling 只缓慢回填。`TrackMask` 仍承担“能否被威胁追踪”的精细视觉与寿命，雪深层只承担体积、速度和地面轮廓，二者不能重复模拟同一件事。

5. **消融严格受世界观约束**

   当前游戏设定持续严寒，常规的晴天不能把雪融回去。只有未来引入明确的零上天气或局部火源热场时，才允许 `thaw` 产生局部消融；在此之前，清朗/静风只会让雪稳定、压实、被极慢地风蚀，不会制造“白天化雪”的反常画面。

## 空间、种子与存档策略

### 基础场：无限可查询，固定可学习

以一个 `run_seed` 派生全部基础噪声和每个固定世界坐标的初始雪深。相同种子、相同数据版本、相同位置必须得到相同结果；窗口移动、读写顺序和帧率不应改变它。这延续现有世界锚定的优点，也使玩家在同一局中能记住“教堂回家应绕开那片雪坑”。

### 动态场：只保存被天气或行动改写的稀疏瓦片

不要保存整座山谷的浮点贴图，也不要每帧扫描 512²。为活动雪窗维护 `R16` 深度增量和现有压实层；按例如 16×16 或 32×32 texel 分块，只更新：

- 玩家附近、镜头可见区；
- 最近被降雪/风影响而标脏的块；
- 建筑门口、道路和玩法地点的常驻小块。

窗口离开时，将非零动态块序列化为稀疏记录；未被改写的远处块重新由基础场即时推导。存档至少保存：`run_seed`、雪模型/数据版本、世界时钟、当前天气状态与随机流状态、稀疏动态块、压实块、已登记的建筑 carve。加载后同样的输入轨迹应恢复相同地面；不同帧率的运行只允许在量化误差内一致。

### 更新节奏

地面雪深以固定模拟步长（建议 0.5–1.0 s，暴雪中可 0.25–0.5 s）批处理；视觉贴图仅上传脏矩形，每帧最多一次。天气只是改变输入率和方向，绝不触发全图重建。这样雪形“在一段时间后可被察觉”，而不会像材质动画一样蠕动。

## 数据驱动接口

一次性新增通用定义后，新增天气或雪型不应再改 GDScript。

| 定义 | 建议位置 | 核心数据 |
|---|---|---|
| `SnowFieldProfile` | `data/snow/valley_profile.tres` | 初始深度范围、目标分布、相关尺度、地形/坡向/遮蔽权重、压实/回填、更新预算 |
| `SnowResponseDefinition` | `data/snow/responses/*.tres` | 沉降率、迎风侵蚀、下风沉积、方向采样距离、上限、是否允许 thaw |
| `SnowSurfaceDefinition`（如确有多材质地面） | `data/snow/surfaces/*.tres` | 路、林地、开阔坡、屋檐下的可积雪性、压实与风蚀系数 |
| `SnowShelter` 烘焙/布置数据 | 地点数据或程序化布局输出 | 建筑、树篱、岩壁对风的遮蔽与禁雪区；不是每帧 raycast |

`WeatherEventDefinition` / `WeatherTell` 只引用 `SnowResponseDefinition`。天气系统在阶段变化时通过 `EventBus` 发布语义化的雪输入快照；雪场缓存该输入，在自己的固定步长内读取风向/风强。不要以每帧事件广播逐格深度，也不要让 `SnowField` 直接认识 `WeatherSystem`、玩家或建筑脚本。

建议事件边界为：`snow.inputs_changed`（天气阶段/天气 response 切换）、`snow.surface_registered`（地点/建筑/道路提供烘焙约束）、`track.footprint`（已有）。风强可按现有服务查询或被输入适配器缓存；关键是保持跨系统零直接引用和可替换的测试注入 seam。

## 与现有玩法的关系

- **移动**：继续由 `SnowField.wade_factor()` 读取；深雪变成可绕开的局部风险，而不是整局二元惩罚。道路和常用归途可以被压成更好的路，但不应奖励出超过浅雪跑速。
- **足迹与威胁**：深度场改变脚印的压实量、边缘和玩家声响/步态的条件；`TrackMask` 继续决定足迹的可见/可追踪寿命。强风可以同时吹薄暴露雪面、快速抹去动态足迹，背风处则仍留较深的雪和较持久的痕迹，形成可读的风险取舍。
- **建筑与信标**：建筑 carve、门口雪舌、火源附近的未来局部 thaw 是硬边界。信标附近不应凭空形成安全的“无雪圆”，除非世界观明确该处有热源或人工清雪。
- **美术**：宏观雪深只让地面轮廓和通行感改变；细节线仍交给车辙、足迹、风雪与阴影。避免在平静时持续重塑雪面，以保护“近乎无纹理的雪”和诗意的静止感。

## 验收与捕捉计划

1. **确定性**：同种子、相同天气时间线、不同窗口移动路径得到相同位置的初始/动态深度；存档加载后与未中断运行一致。
2. **分布质量**：对批准的多个种子扫描可行走区域，验证浅/中/深三段都存在；当前基准中 0.02–0.32 m 的 12 m 中间带已存在，必须保留。具体分位数、最小占比和首日安全路径下限需由玩法负责人签字后写入测试，而不是在代码里臆定。
3. **物理不变量**：深度非负且有 profile 上限；室内为零；无 thaw 时清朗天气不产生全局融雪；风蚀仅从暴露侧向背风侧搬运或作为明确的窗口流失；压实不增加雪深。
4. **性能**：记录每次固定步更新的脏块数、像素写入数和上传次数；验证静风时不扫描全窗口，暴雪也不出现每帧全图上传。
5. **视觉/玩法 capture**：用固定种子在晨、静风、横风、暴雪前后，从四个风向拍同一处路、树、门和低洼处；再用不同种子拍同一任务路径。Godot AI capture/scene inspection 若在运行环境中可调用，应保存这些可比较截图和深度探针读数。

## 分阶段落地

### Phase A — 锁定基础分布基准（Wave 4 的前置）

测量当前深度直方图、12 m 区块均值、地点/首日路线的可通行性；保留固定种子扫描器和“中间带没有消失”的回归门禁。2026-08-13 的复测已经确认中间深度并未缺失，因此在负责人签署目标分位数和安全路线下限前，不改 `SnowField` profile，也不以消费者参数掩盖生成问题。

### Phase B — 每局种子化初始雪层

由 run owner 生成并持有 `run_seed`，将其显式注入雪场；实现固定世界坐标的基础场和安全区约束。验收“同局稳定、异局不同、剧情路线仍可走”。此阶段即可满足“每局不再固定不变”。

### Phase C — 稀疏动态深度层

增加脏瓦片、固定步更新、雪输入 response 与连续沉降；将现有压实从“唯一变化”纳入同一层。先只在降雪下缓慢增加，确保没有 pop。

**当前实现边界。** Phase C 的稀疏瓦片首先是可复现的玩法事实：`SnowField.depth_at()` 和涉雪/压实读取它，但现有地表 shader 尚不上传或采样该增量。因此本阶段不会用假贴花、雾或材质滚动去伪装“雪变深”；视觉上仍以既有地形、足迹与降雪承接变化。

**后续视觉桥接。** 待方向性风、遮蔽和存档的动态块格式稳定后，再将同一批非零瓦片合成为有版本的动态 R16 增量纹理，只上传脏矩形、每帧最多一次。shader 只能读取这个派生纹理，不能反向决定玩法深度；这样渲染与存档回放都来自同一份世界锚定数据。

### Phase D — 方向性风搬运与地点遮蔽

接入风向/强度和预计算 shelter，加入保守的侵蚀—沉积。以白茫、静风、风向突变三类真实数据事件做 capture 验收；建筑/门口 carve 回归测试必须先绿。

### Phase E — 存档、长局与调优

实现稀疏块序列化、版本迁移、性能计数器和端到端回放；随后再调足迹尺寸、涉雪速度和威胁读取。消费者参数只能在新分布稳定后重调，避免用表现层掩盖生成问题。

## 需要负责人先裁决的边界

1. 每局地貌差异的幅度：建议只改变“可选路线与局部风险”，不改变固定叙事地点的位置或让 Day 1 失去安全路线。
2. 雪深是否跨死亡/重开保存：设计上建议一次 run 固定，死亡重开以新种子或明确的“重试同一天候”规则决定，不能悄然混用。
3. 是否让火源拥有真实局部融雪：这会改变室内/营地的视觉与玩法，目前世界观没有现成温度场，必须由世界观和生存系统负责人共同批准后再加入。
4. 目标深度分布与每种天气的输送上限：应先由固定种子 capture 和路线时间测量决定，再成为 data/test 的硬门槛。

## 1. 当前结论

项目已经不是旧看板所写的“Wave 0、98 个测试、尚无场景”。当前仓库已有可运行主场景、玩家移动、雪地与足迹、天气和光照、生存数值、燃料与火炉、农舍室内、信标、四条生存路线、环境音、交互反馈、暂停/退出界面及 Windows 导出流程。

现阶段最大问题不是缺少系统，而是多个方向同时继续加细节，导致“能运行的垂直切片”与“完整七日生存游戏”之间缺少一条清楚的验收主线。因此从本次基线起，开发顺序改为：先闭合七日循环，再做威胁和结局，最后统一做视觉与内容验收。

### 阶段 1 当前进展

第一切片已完成运行所有权：`GameState` 取代临时 `RunBoot`，原子启动生存模型与七日时钟，并在死亡、五座信标全亮、仍有信标熄灭三种终态中只结算一次。真实的 7 份日程与 5 份信标数据已有确定性第八天黎明出口测试。

下一切片：为燃料库存、路线拾取物和信标油量增加统一的重开复位契约；在此之前，`GameState` 明确拒绝从终态只重置半套世界。

## 4. 冻结规则

- 新的视觉打磨与截图驱动微调；

## 5. 后续开发计划

### 阶段 1：闭合七日生存循环

目标：从启动新游戏到第 7 天结束，玩家可以通过路线搜集资源、维持生存、点亮信标，并稳定到达成功或失败结算。

出口条件：

1. 新游戏、每日推进、天气调度、生存消耗、燃料、路线资源、信标状态组成一条确定性的端到端测试；
2. 死亡、燃料耗尽、关键资源不足都有明确且可恢复的结果；
3. 所有跨系统通信继续经过 `EventBus`，内容继续由 `.tres` 驱动；
4. 完整套件和一条实际游戏 smoke test 同时通过。

### 阶段 2：威胁与结局

目标：只在七日循环稳定后加入威胁框架、饿汉/熊、武器、客人事件和三种结局。

顺序：威胁通用框架 → 两份数据化威胁 → 武器/回避手段 → 客人事件 → 三种结局 → 存档与死亡恢复。

出口条件：新增威胁主要通过数据完成；三种结局各有自动化路径；失败恢复不会破坏七日状态。

### 阶段 3：统一体验验收

目标：集中处理已冻结的视觉、音频、动物、UI 和道具工作，避免再次多线失焦。

顺序：农舍进出体验 → 天气可读性 → 昼夜与火光 → 遮挡/雪地身体显示 → 动物与环境叙事 → UI/暂停菜单 → 新道具。

每一项必须有同一机位的前后截图、手动验收清单和对应回归测试；未通过的项目不扩展到下一个视觉主题。

### 阶段 4：性能与发布

目标：在功能和画面稳定后完成硬件矩阵、Windows 包体、长时间运行、存档兼容和发布清单。

## 6. 当前最高风险

| 风险 | 处置 |
|---|---|
| 自动化测试很多，但缺少完整游戏路径 | 阶段 1 第一任务就是七日端到端出口测试 |
| 主场景承担过多系统集成，提交边界容易互相污染 | 后续每个阶段只允许一个主线集成窗口；共享场景改动最后落地 |
| 本地资产被 `.gitignore` 排除，远端不能单独复现全部画面 | 保持现行大资产策略，但发布阶段必须增加资产包版本清单和校验 |
| `DEFERRED.md` 已很长且混入历史裁决 | 阶段 1 只提取阻塞当前出口条件的条目，不再顺手处理远期欠账 |
| “看起来完成”与“可玩闭环完成”混淆 | 进度只按出口测试计数，不按文件数、截图数或局部效果计数 |

## 7. 每次主线提交的固定出口

1. `bash tools/run_tests.sh` 控制台完全洁净；
2. 相关功能至少有一个会失败的回归断言；
3. 不提交 `build/`、缓存、一次性探针和本机路径；
4. 更新本文件时只记录仓库事实和已跑出口，不记录计划中的“预计完成”；
5. 在阶段 1 结束前，不接收冻结列表中的新功能。

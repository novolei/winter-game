# WinterTime — 项目主线与开发进度

最后更新：2026-08-14

基线分支：`main`

当前阶段：阶段 1「闭合七日生存循环」进行中
健康状态：绿色（主线测试基线 `2416 passed, 0 failed`，出口脚本与控制台门禁均通过）

## 1. 当前结论

项目已经不是旧看板所写的“Wave 0、98 个测试、尚无场景”。当前仓库已有可运行主场景、玩家移动、雪地与足迹、天气和光照、生存数值、燃料与火炉、农舍室内、信标、四条生存路线、环境音、交互反馈、暂停/退出界面及 Windows 导出流程。

现阶段最大问题不是缺少系统，而是多个方向同时继续加细节，导致“能运行的垂直切片”与“完整七日生存游戏”之间缺少一条清楚的验收主线。因此从本次基线起，开发顺序改为：先闭合七日循环，再做威胁和结局，最后统一做视觉与内容验收。

### 阶段 1 当前进展

第一切片已完成运行所有权：`GameState` 取代临时 `RunBoot`，原子启动生存模型与七日时钟，并在死亡、五座信标全亮、仍有信标熄灭三种终态中只结算一次。真实的 7 份日程与 5 份信标数据已有确定性第八天黎明出口测试。

第二切片已完成统一重开复位：`GameState.restart_run()` 在新局启动前同步发布值类型 `game.run_reset`；`FuelEconomy` 清空库存但保留目录，`SurvivalRouteLayer` 恢复已拾取节点，`BeaconNetwork` 清空燃料和火焰、重置随机种子并恢复第 1 天解锁边界。重置顺序、重复拾取和五座信标归零均已有回归测试。

第三切片已完成确定性领域闭环：天气首局从 `GameState` 的运行种子取值，`game.run_reset` 会清空正在进行和排队中的天气并重置随机序列；路线既有节点补齐七日所需的 14 份罐头和 14 份雪。固定种子 `1729` 的测试以一秒步长推进真实 6300 秒日程，交错运行天气、生存、炉火、路线、信标和 `GameState`，验证暴雪预警/抵达/熄灯/重燃、角色存活、五灯全亮、救援结算和完整燃料守恒。

第四切片已接通关键玩家入口：火炉通过既有 `InteractionDirector` 和投喂鸽子同款圆环 E 提示，短按每次只执行提示中的一个原子家务，长按 0.8 秒可在任意家务状态下熄火并保留炉内燃料；连续短按仍可逐件补燃料到炉子容量。家务顺序由物品定义和真实饥渴容量决定，炉边不新增面板或垂直引导线。提示后的库存竞态只会拒绝，不会改做另一件事。`NightExposure` 同时订阅真实 `interior.entered/exited`；重复进出事件保持幂等，`clock.run_finished` 会清除夜间与庇护状态。

第五切片已闭合失败反馈与死亡重开：炉边继续复用同一 E 圆环和既有交互回执，不增加库存面板；短按会精确说明燃料不足、加工热量不足、没有食物或没有水，长按熄火仍始终可达。炉火和信标因燃料耗尽而熄灭时会显示一次短暂结果，手动或天气熄火保持静默。死亡由独立终局层接管暂停，只呈现“第 N 日。”；普通暂停菜单不能给出错误的“继续”。E 重开严格等待 `game.run_reset → clock.day_started → game.run_started` 成功后才调用主场景重载，夜间庇护、音乐终局状态和音乐随机序列同步清理；弃置结局按设计不创建任何 Control。

真实 `scenes/main.tscn` smoke test 现同时覆盖两条产品链：其一是在实时场景树中完成 3 次路线拾取 E、5 次炉边短按和 1 次炉边长按，以及农舍进出对夜间体温倍率的移除和恢复；其二是真实炉火燃尽、真实炉边短缺拒绝、真实生存耗尽死亡、玩家 E 重开、领域复位和场景重载调用。测试不直接伪造 `survival.died`，也不直接调用 `GameState.restart_run()`。它仍不冒充完整 6300 秒人工游玩。阶段 1 的自动化出口已闭合；下一主线切片只处理启动画面期间运行已提前开始的问题，并完成一次完整人工七日验收，不开始新的视觉或内容工作。

## 4. 冻结规则

阶段 0 完成后，以下内容继续冻结，直到阶段 1 的玩家可达七日循环与真实场景 smoke test 同时通过：

- 新的视觉打磨与截图驱动微调；
- 新动物行为、鸽子功能和额外动画；
- 暂停菜单、退出菜单和无障碍界面的进一步润色；
- 新道具、新建筑和新的场景装饰；
- 不服务于七日循环出口条件的性能微优化。

允许的改动只有：阻塞主线的缺陷、出口测试、数据一致性、崩溃/闪烁/穿模等严重回归，以及完成当前阶段所需的文档和构建修复。

## 5. 后续开发计划

### 阶段 1：闭合七日生存循环

目标：从启动新游戏到第 7 天结束，玩家可以通过路线搜集资源、维持生存、点亮信标，并稳定到达成功或失败结算。

出口条件：

1. 新游戏、每日推进、天气调度、生存消耗、燃料、路线资源、信标状态组成一条确定性的端到端测试；
2. 死亡、燃料耗尽、关键资源不足都有明确且可恢复的结果；
3. 所有跨系统通信继续经过 `EventBus`，内容继续由 `.tres` 驱动；
4. 完整套件和一条实际游戏 smoke test 同时通过。

### 阶段 2：威胁与结局

目标：只在七日循环稳定后加入威胁框架、饿汉/熊、武器、客人事件和三种结局。

顺序：威胁通用框架 → 两份数据化威胁 → 武器/回避手段 → 客人事件 → 三种结局 → 存档与结局恢复。

出口条件：新增威胁主要通过数据完成；三种结局各有自动化路径；失败恢复不会破坏七日状态。

### 阶段 3：统一体验验收

目标：集中处理已冻结的视觉、音频、动物、UI 和道具工作，避免再次多线失焦。

顺序：农舍进出体验 → 天气可读性 → 昼夜与火光 → 遮挡/雪地身体显示 → 动物与环境叙事 → UI/暂停菜单 → 新道具。

每一项必须有同一机位的前后截图、手动验收清单和对应回归测试；未通过的项目不扩展到下一个视觉主题。

### 阶段 4：性能与发布

目标：在功能和画面稳定后完成硬件矩阵、Windows 包体、长时间运行、存档兼容和发布清单。

## 7. 每次主线提交的固定出口

1. `bash tools/run_tests.sh` 控制台完全洁净；
2. 相关功能至少有一个会失败的回归断言；
3. 不提交 `build/`、缓存、一次性探针和本机路径；
4. 更新本文件时只记录仓库事实和已跑出口，不记录计划中的“预计完成”；
5. 在阶段 1 结束前，不接收冻结列表中的新功能。
